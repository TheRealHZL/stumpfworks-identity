# v1.2 client management

The first v1.2 increment adds a deliberately narrow, server-side foundation for centrally visible client health. It does not change the badge, PIN, PAM, PKINIT, Kerberos, or CIFS paths and is not deployed automatically.

## Security model

- An administrator provisions a client locally on LOGIN01 with `sw-badge-server -config /etc/stumpfworks-badge/config.yaml -register-client <client-id>`.
- The command prints a cryptographically random bearer token exactly once. Only its SHA-256 hash is stored in SQLite.
- A client may submit only its own bounded status document to `POST /api/v1/client/status` over the existing verified TLS connection.
- `GET /api/v1/clients` remains behind the existing administrator session guard.
- Status values are limited to `unknown`, `ok`, `degraded`, or `unavailable`. Version and client ID lengths are bounded; unknown JSON fields and bodies over 4 KiB are rejected.
- Status reports contain no usernames, network addresses, SSIDs, badge data, PINs, tokens, private keys, logs, or free-form diagnostic text.

## Status document

```json
{
  "client_id": "wyse01-greeter",
  "version": "1.2.0-dev",
  "network_status": "ok",
  "ad_status": "ok",
  "camera_status": "ok",
  "kerberos_status": "unknown"
}
```

## Client collector

`sw-badge-client-status` is a short-lived process started by `swbadge-client-status.timer`. It reports once and exits. The collector checks only:

- whether a non-loopback interface is up and has a non-link-local address;
- whether `wbinfo -t` confirms the existing Winbind trust;
- whether a `/dev/video*` device exists;
- whether `kinit` and the PKINIT plugin are installed.

It does not enumerate or transmit interface names, addresses, SSIDs, AD users, logged-in users, Kerberos principals, logs, or command output. HTTPS is mandatory and the configured Homelab CA remains in use.

The guided client installer accepts the one-time provisioned token, stores it as root-only mode `0600`, installs the collector and enables its timer. It performs one immediate status submission but does not restart LightDM unless separately confirmed.

The protected LOGIN01 system-status page renders all registered clients and labels reports older than three minutes as stale. Fresh reports are healthy only when every bounded readiness check is `ok`; otherwise they are marked for attention. Clients that have not submitted a report are shown separately.

Token rotation and revocation should be implemented before broad deployment.
